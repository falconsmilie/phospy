# Validation Ownership Map

This map defines primary ownership for high-impact validation invariants.
Higher-level layers may compose owners, but must not duplicate ownership logic.

This is a maintainer architecture reference. Users diagnosing an input or
workflow error should start with the [Validation Guide](validation.md).

## Ownership Notes

- Dataset validation remains private and construction-bound: there is no public
  dataset `validate()` API.
- Public constructor validation is explicit:
  - Passive request DTOs (`DatasetBuildRequest`, `PhosphositeImportRequest`,
    `DifferentialAnalysisRequest`, `EnrichmentWorkflowRequest`,
    `KinaseWorkflowRequest`, and `SignalomeWorkflowRequest`) store payloads only.
    Request type compatibility, contextual compatibility, and scientific
    readiness are validated by the owning builder or workflow validator.
  - Generic public value objects in `phospy.contracts` and public
    design/enrichment contract objects validate only local, context-free
    scalar/container invariants during construction and raise
    `ContractValidationError`.
  - Dataset constructors raise dataset-boundary validation errors
    (`DatasetValidationError`) for strict analysis-ready dataset invariants.
  - Reference bundle/resource constructors raise reference-boundary validation
    errors (`ReferenceValidationError`) for reference structural invariants.
  - Dataset-build preprocessing config constructors are builder-input policy
    value objects. They validate local preprocessing option shape and continue
    to raise `PhosPyInputError`, while data-dependent preprocessing eligibility
    remains in the builder validation path.
- Users validate dataset inputs by constructing datasets through supported
  builders, or by running workflows that validate requests at their boundary.
  Direct imports or calls into `phospy.validation.datasets` are internal support
  paths for package code and tests, not supported user entrypoints.
- Validation-domain adapters may call dataset construction, but they must not
  reimplement `AnalysisReadyPhosphoDataset` invariants.
- Validation-domain compatibility routes may re-export science-owned
  model-boundary validators, but value objects must not import validation
  modules to validate themselves.
- Validation-domain identity and sequence-context compatibility routes must
  preserve object identity with the science-owned contract classes and
  enforcement functions.
- The group-coverage validation-domain facade must preserve object identity
  with the preprocessing-owned coverage validator, result type, and numeric
  matrix check. Generic sample-group resolution and coverage-specific checks
  remain science/preprocessing-owned and must not import that facade.
- Workflow validators should compose shared/domain validators instead of duplicating row-level scientific identity checks.
- Initial workflow validators own request, dataset, and configuration invariants
  available before interpretation. Resolved validators own scientific
  eligibility checks that require interpreted references, configuration, or
  executable inputs. Executors do not become validation owners beyond defensive
  internal checks.
- Scientific caveats follow
  [ADR-0033](adr/adr_0033_result_caveats.md): validators and interpreters
  produce structured facts, result assemblers attach user-facing top-level
  `caveats`, and severe caveats must not be log-only.
- Caveats complement provenance. They should summarize interpretation risks,
  limitations, assumptions, and policy overrides without duplicating full
  provenance payloads or becoming arbitrary message containers.
- Public request dataclasses remain transport objects; boundary ownership sits in validators and domain contracts.
- Differential replicate policy is owned by the public
  `DifferentialAnalysisWorkflow.run(...)` pipeline through reliability,
  experimental-design, planner, and aggregator collaborators. The former
  `TechnicalReplicateResolver` wrapper was removed by ADR-0054. Numerical
  executors must receive already-validated matrices and
  must not reinterpret technical or biological replicate semantics.
- Policy enums are owned by behavioural domain modules:
  - preprocessing: `phospy.preprocessing.contracts.policies`
  - differential: `phospy.differential.policies`
  - kinase scoring: `phospy.kinase.scoring.policies`
  - shared policy-enum infrastructure: `phospy.policies.policy_base`
  - root module `phospy.policy_models` has been removed.
- Scientific table schemas are owned by their domain packages, including
  `phospy.datasets.schemas`, `phospy.differential.tables`, the Kinase table
  modules, `phospy.references.tables`, and `phospy.signalome.tables`. Generic
  table-schema infrastructure is owned under `phospy.frames`. The former
  `phospy.tables` forwarding package was removed by ADR-0054.
